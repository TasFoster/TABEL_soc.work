# Сборка, выпуск и обновления

## GitHub Releases

Основной канал обновления — публичный репозиторий `TasFoster/TABEL_soc.work`.
Программа читает `https://github.com/TasFoster/TABEL_soc.work/releases/latest/download/version.json`.
Манифест содержит отдельные записи `full`/`lite`, точные ссылки на установщики
конкретного тега, размеры и обязательные SHA-256. Токен пользователю не требуется.
Репозиторий и assets должны оставаться публичными, GitHub должен быть доступен с ПК.

Проверка запускается в фоне при открытии программы и по кнопке. Установка — по кнопке
«Обновить сейчас», с закрытием приложения; portable-копия только скачивает установщик.
Существующие AppId, каталоги и правило `onlyifdoesntexist` для данных сохранены.
В сборку не копируется рабочая БД разработчика.

## Как выпустить новую версию

1. Внести проверенные изменения в `main`.
2. Обновить `tabel_app/RELEASE_NOTES.md` и увеличить `tabel_app/VERSION` (например, `1.8.3`).
3. Отправить изменения одним коммитом. Изменение VERSION запускает workflow
   **Windows installers**. Первое добавление workflow тоже запускает сборку.
4. В Actions проверить успешное завершение: тесты, полная и облегчённая сборки,
   проверка импорта функций/версии/OCR в собранном EXE, компиляция Inno Setup.
5. Workflow сохраняет артефакт с обоими установщиками и `version.json`, затем
   публикует полный релиз `v<версия>`. До загрузки всех assets релиз остаётся черновиком.

`version.json` создаётся из готовых установщиков, вручную его редактировать не нужно.
Номер читается из VERSION и встраивается в EXE, Inno Setup и манифест.
Установщики называются `Tabel-full-setup.exe` и `Tabel-lite-setup.exe`.
Повторная публикация уже опубликованной версии запрещена — увеличить VERSION.
Повторный запуск после ошибки допускается для черновика только с тем же commit SHA.
Нельзя переиспользовать тег старого черновика для изменённых исходников.

Ручной запуск: GitHub → Actions → Windows installers → Run workflow → main.
Требуются включённые Actions и разрешение workflow `contents: write`. Используется
автоматический `GITHUB_TOKEN`, личные токены и пароли в исходники не добавляются.

## Переход с Яндекс.Диска

Версии до этого выпуска знают только Яндекс.Диск. Для перехода:

- либо вручную установить новый установщик поверх существующей установки;
- либо разместить новый `version.json` и оба установщика в прежней публичной папке
  Яндекс.Диска. Старый updater поддерживает поле `url` и скачает установщик с GitHub.

После перехода следующие версии проверяют GitHub. Сама публикация в GitHub не меняет
манифест на Яндекс.Диске; обновить его нужно отдельно. Старый адаптер сохранён в коде,
но автоматического возврата на устаревший манифест при ошибке GitHub нет.

## Локальная Windows-сборка

Python 3.11 x64, Inno Setup 6, PowerShell и GitHub CLI (для публикации).

```powershell
python -m pip install -r tabel_app/requirements-build.txt
powershell -ExecutionPolicy Bypass -File tabel_app/tools/build_release.ps1 -OutDir C:\tabel-release
```

Новый генератор: `tools/make_manifest.py`. Прежний `tools/make_manifest.ps1` предназначен
для старой ручной упаковки Яндекс.Диска; в GitHub workflow он не используется.
Сборочные скрипты PowerShell остаются ASCII-only, `.iss` сохраняются в UTF-8 с BOM.

## Проверки без Windows

```sh
python -m unittest discover -s tabel_app/tests -v
```

Эти тесты проверяют выбор варианта, ссылки манифеста, размеры, хеши, отказ при неверном
хеше и сохранение локального тестового источника. Они не заменяют запуск Windows EXE,
проверку распознавания реальных билетов и установку поверх существующей версии.
